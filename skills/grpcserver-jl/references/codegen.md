# Code generation (`protojl`)

The codegen interface is the primary way to build a gRPCServer.jl server: one
`protojl` run over a `.proto` file emits message types, gRPCClient client stubs,
and gRPCServer registration functions in one generated module.

## Invocation

```julia
using ProtoBuf
using gRPCServer       # mandatory BEFORE protojl: registers the server codegen hook
import gRPCClient      # mandatory BEFORE protojl if you want client stubs

protojl("greeter.proto", "proto", "generated";
    always_use_modules  = true,
    add_kwarg_constructors = true)
```

- `protojl` is re-exported by gRPCServer, so `using gRPCServer` alone is enough
  for the call itself; `using ProtoBuf` is shown for clarity.
- Arguments: the `.proto` file (relative to cwd), the search root used to
  resolve `import` statements inside the proto, and the output directory.
- `always_use_modules = true` wraps each package's output in a module.
  `add_kwarg_constructors = true` adds keyword constructors to the message
  structs. Both are the settings used by the test suite and the examples.
- Loading `gRPCServer` registers the codegen hook automatically from `__init__`
  via `grpc_register_service_codegen()`; no manual registration is needed.
  `grpc_register_service_codegen()` is exported and can be called again to
  re-register.

## Output layout

For `package helloworld` in `greeter.proto`:

```
generated/
└── helloworld/
    ├── helloworld.jl      # module wrapper: module helloworld; include("greeter_pb.jl"); end
    └── greeter_pb.jl      # the content: messages, client stubs, registration functions
```

Use it like this:

```julia
include("generated/helloworld/helloworld.jl")
using .helloworld
```

The header is `# Autogenerated using ProtoBuf.jl v1.3.0` with the relative proto
path and `(proto3 syntax)` — no timestamp, no absolute machine paths (older
ProtoBuf versions emit timestamps and absolute paths; if you see those, check
the ProtoBuf version).

## Emitted symbols

Per service, the generated `*_pb.jl` contains, for every RPC:

| Symbol | Shape | Notes |
|---|---|---|
| Method builder | `<Service>_<Rpc>_Method(handler; raw_request=false, raw_response=false) -> gRPCServer.MethodDescriptor` | Builds the descriptor; validates the handler shape at construction |
| Per-RPC registration | `register_<Service>_<Rpc>!(server::GRPCServer, handler; raw_request=false, raw_response=false) -> server` | Also emitted in reversed argument order `(handler::Function, server::GRPCServer; kwargs...)` so the do-block form works |
| Aggregate | `register_<Service>!(server::GRPCServer; <Rpc>=nothing, ...) -> server` | One keyword per RPC; each accepts a handler or a `(handler, raw_request, raw_response)` tuple; all-nothing is a no-op |
| Client | `<Service>_<Rpc>_Client(host, port; TRequest=..., TResponse=..., grpc=gRPCClient.grpc_global_handle(), options...)` | The gRPCClient.jl constructor; hits `/{package}.{Service}/{Rpc}` |

Every emitted symbol is exported and carries a static docstring with its typed
handler contract — the IDE-hover deliverable.

The file is delimited into `# gRPCClient.jl BEGIN/END` and
`# gRPCServer.jl BEGIN/END` blocks. Keep both when you regenerate; the client
stubs are cheap and let you smoke-test the server from Julia.

## Service names and paths

- The gRPC service path is `/{package}.{Service}/{Rpc}` — e.g. proto
  `package helloworld; service Greeter { rpc SayHello ... }` serves
  `/helloworld.Greeter/SayHello`.
- Registration functions are named from the *service* and *rpc* identifiers:
  `register_Greeter_SayHello!`, `register_Greeter!`. A client built from a
  different package or service name will 404 with `UNIMPLEMENTED`.

## Registration-time validation

Handlers are checked when registered, not when a request arrives. The check is
the RPC kind (unary vs streaming), the request/response types, and the raw
flags. A mismatch throws `ArgumentError` immediately. The aggregate keyword
form unpacks `(handler, raw_request, raw_response)` tuples the same way the
per-RPC function does.

## Regeneration and byte-stability

Generation is deterministic for a given ProtoBuf + Julia version: same input,
same output, byte for byte. This is relied on by the test suite and the
examples. Practical rules:

- Regenerate from the same directory with the same relative paths, or headers
  (which record the proto path) will differ.
- Do not hand-edit generated files; regenerate instead.
- If byte-stability across two runs ever breaks, the first suspect is a
  different ProtoBuf version in the active environment.

## Verifying generation

```julia
# parses and loads the module?
include("generated/helloworld/helloworld.jl")
using .helloworld

# all expected symbols present?
@assert isdefined(helloworld, :Greeter_SayHello_Method)
@assert isdefined(helloworld, :register_Greeter_SayHello!)
@assert isdefined(helloworld, :register_Greeter!)
@assert isdefined(helloworld, :Greeter_SayHello_Client)
```

See `references/handlers.md` for what to do with the registration functions,
and the `grpcserver-jl-dev` skill for regenerating the repo's own examples.
